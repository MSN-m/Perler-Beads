# 拼豆项目产品护栏与变更规则

> 用途：在开发过程中保护已确定的用户流程和产品边界。本文不是实现说明，而是修改代码前的决策与验证规则。

## 1. 核心流程不得被悄悄改变

以下流程属于产品核心。任何会改变步骤、入口、默认行为或数据结果的改动，都必须先说明影响范围与风险，等待用户确认后再编辑：

1. 上传图片 -> 确认裁剪范围 -> 设置 -> 生成预览 -> 选择效果 -> 编辑 -> 保存/导出。
2. 草稿的保存、恢复、导出、导入和删除。
3. 图纸编辑、撤销、重做和暂存修改。
4. 品牌、规格、颜色限制与图纸尺寸对最终图纸的影响。
5. 图纸导出内容、名称和色号统计。

纯视觉样式、间距、颜色、图标和已确认的响应式布局调整，通常可以直接实施；只要不改变功能入口、状态转移或操作语义。

## 2. 修改前必须预警的情况

出现以下任一情况时，先向用户报告“将影响什么、可能丢失什么、如何验证”，不要直接改动：

- 删除、合并、隐藏或改名现有核心操作。
- 改变生成算法的默认路径、颜色匹配、抖动、颜色限制或图纸尺寸计算。
- 改变 `AppState.pixelData`、`stagedPixelData`、撤销/重做或草稿数据结构。
- 修改画布坐标、缩放、平移、触控或编辑工具互斥关系。
- 将实验页面的算法或 UI 直接接入正式 `index.html` 流程。
- 改变 PC、PAD、手机三端的功能可用性，或让某端失去既有能力。
- 修改导出格式、草稿格式或本地存储键。

预警应至少包含：受影响的流程、受影响端、回归测试项，以及是否可恢复。

## 3. 不可破坏的状态边界

- 正式图纸数据与编辑暂存数据必须分开；编辑过程不能无提示覆盖正式图纸。
- 撤销/重做必须覆盖编辑器的全局操作，并保持与暂存区一致。
- 编辑模式与画布拖拽必须互斥；进入调整或删除模式时，不得触发普通平移。
- 颜色清单只能表示“当前图纸已使用的颜色”，不是完整品牌色板。
- 全部颜色属于品牌完整色板入口；选色后应成为画笔当前颜色。
- 生成预览不应未经用户确认直接覆盖已有正式图纸或编辑结果。
- 重新应用生成设置可能覆盖编辑结果时，必须给出明确提示。

## 4. 生成算法边界

- 当前正式生成器继续使用现有网格化拼豆流程。
- 已选择“中强度区域级扁平化 + 主体与背景分离”作为后续正式方向，但其实现尚未完成正式接入。
- `algorithm-lab.html`、`algorithm-lab-complete.html`、`flatness-lab.html`、`combined-lab.html` 和实验函数只用于测试、比较与参数验证。
- 实验算法要进入正式流程前，必须得到明确确认，并完成以下验证：
  - 与裁剪、尺寸、品牌、规格、颜色限制兼容。
  - 与预览确认、编辑、草稿恢复和导出兼容。
  - 使用代表性图片验证轮廓、颜色准确性（含亮度/饱和度偏移）、还原精准度、颜色数、孤立色块和生成耗时。
  - 不降低 PC、PAD、手机端主流程稳定性。

## 5. 三端适配边界

- 允许 PC、PAD、手机各自拥有不同 UI，但功能语义和数据结果必须一致。
- PC 以完整编辑能力为优先。
- PAD 以大画布、触控和制作辅助为优先；设置、颜色与草稿面板不应长期压缩画布。
- 手机以分步操作、明确状态和安全触控为优先。
- 任何新增手势都必须避免与画布拖拽、缩放和编辑点击冲突。

## 6. 高风险模块与最低验证

| 修改区域 | 修改后最低验证 |
| --- | --- |
| `src/processor.js` | 上传图片、不同尺寸、颜色限制、预览、最终生成、耗时与颜色统计。 |
| `src/renderer.js` / 画布事件 | 缩放、拖拽、点击格子、编辑模式、PC 与触控端。 |
| `src/editor.js` / `src/features/adjust.js` | 画笔、吸管、橡皮、批量替换、撤销、重做、暂存与确认。 |
| `src/ui.js` / `src/main.js` | 上传、裁剪、设置、生成、面板、草稿、导出。 |
| `index.html` / `css/style.css` | PC、PAD、手机的可见性、层级、点击与滚动。 |
| 草稿或导出逻辑 | 保存、恢复、导入、导出、图纸名称和颜色统计。 |

## 7. 开发前后的执行规则

开发前：

1. 阅读 `docs/PROJECT_CORE.md`、本文和最新开发归档。
2. 阅读将被修改函数的完整实现，并搜索所有调用方。
3. 判断本次属于普通样式调整还是核心流程变更。
4. 若属于核心流程变更，先提出影响说明与确认请求。

开发后：

1. 检查 JavaScript 语法与补丁格式。
2. 测试直接修改的功能及其关联流程。
3. 对涉及三端、画布、生成、草稿或导出的改动做对应回归。
4. 在归档中记录已确认决策、遗留风险和下一步验证。

## 8. 维护规则

每次“一键归档”时，检查本文是否仍与产品决策一致：

- 新确认的核心流程要写入。
- 已废弃的限制要删除或标记为历史。
- 实验能力转为正式能力时，要先更新本文，再更新核心说明书和归档。
- 如果一个规则不足以阻止高风险改动，补充具体的触发条件与验证项。
