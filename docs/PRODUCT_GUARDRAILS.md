# 拼豆项目产品护栏与变更规则

> 用途：在开发过程中保护已确定的用户流程和产品边界。本文不是实现说明，而是修改代码前的决策与验证规则。

## 1. 核心流程不得被悄悄改变

以下流程属于产品核心。任何会改变步骤、入口、默认行为或数据结果的改动，都必须先说明影响范围与风险，等待用户确认后再编辑：

1. 上传图片 -> 确认裁剪范围 -> 设置 -> 生成预览 -> 选择效果 -> 编辑 -> 保存/导出。
2. 草稿的保存、恢复、导出、导入和删除。
3. 图纸编辑、撤销、重做和暂存修改。
4. 品牌、规格、颜色限制与图纸尺寸对最终图纸的影响。
5. 图纸导出内容、名称和色号统计。

纯视觉样式、间距、颜色、图标和已确认的响应式布局调整，通常可以直接实施；只要不改变功能入口、状态转移或操作语义。

## 2. 修改前必须预警的情况

出现以下任一情况时，先向用户报告“将影响什么、可能丢失什么、如何验证”，不要直接改动：

- 删除、合并、隐藏或改名现有核心操作。
- 改变生成算法的默认路径、颜色匹配、抖动、颜色限制或图纸尺寸计算。
- 改变 `AppState.pixelData`、`stagedPixelData`、撤销/重做或草稿数据结构。
- 修改画布坐标、缩放、平移、触控或编辑工具互斥关系。
- 将实验页面的算法或 UI 直接接入正式 `index.html` 流程。
- 改变 PC、PAD、手机三端的功能可用性，或让某端失去既有能力。
- 修改导出格式、草稿格式或本地存储键。

预警应至少包含：受影响的流程、受影响端、回归测试项，以及是否可恢复。

## 3. 不可破坏的状态边界

- 正式图纸数据与编辑暂存数据必须分开；编辑过程不能无提示覆盖正式图纸。
- 撤销/重做必须覆盖编辑器的全局操作，并保持与暂存区一致。
- 编辑模式与画布拖拽必须互斥；进入调整或删除模式时，不得触发普通平移。
- 颜色清单只能表示“当前图纸已使用的颜色”，不是完整品牌色板。
- 全部颜色属于品牌完整色板入口；选色后应成为画笔当前颜色。
- 图纸必须至少有一个实际拼豆格。全透明图片不得进入生成流程；任何擦除、移除底色或批量修改若会让整张图纸变空，必须拒绝该操作或回滚，避免留下无法取色的空图纸。
- Figma 工具栏重写已确认：副栏只在选中主工具“画笔”时弹出，用于控制/选择画笔、油漆桶、边框子工具及最近颜色；切换到其他主工具时收起。副栏不再重复放置“全部”色板入口，完整色板由主工具栏“色板(C)”打开，并提供“图纸颜色/全部颜色”切换。边框使用整图轮廓边缘上色语义；拖动是持续生效的独立平移工具；最近颜色显示最近使用的 5 色，不足时按设计稿显示空槽；无手动选色时画笔首次启用自动采用当前图纸数量最多的颜色，且只设置颜色、不改图纸；橡皮支持按住拖动连续擦除。
- PC 快捷键 B/H/I/C/E 已确认。快捷键不得在文本输入控件聚焦时拦截输入。
- 当前实施范围先限 PC。Figma 主栏参考尺寸为 690×72，五个主工具按钮及撤销/重做的图标、颜色、控件尺寸需按设计稿复刻。当前实现的主栏位置、按钮间距和整体布局已被用户指出不正确，必须修正并在图纸编辑态对照 Figma 验收后，才可标记为完成；本条仅记录待办，不要求本轮归档时改代码。
- 工具栏重写必须保留画笔、连通区域油漆桶、整图轮廓边缘上色、单格/连续拖擦/区域/按颜色擦除、吸管、完整色板、最近颜色状态以及全局撤销/重做语义。
- 生成预览不应未经用户确认直接覆盖已有正式图纸或编辑结果。
- 重新应用生成设置可能覆盖编辑结果时，必须给出明确提示。

## 4. 生成算法边界

- 当前正式生成器继续使用现有网格化拼豆流程。
- 当前 `index.html` 使用的现有网格化拼豆流程是已确认的正式方案，保持默认路径不变。
- “中强度区域级扁平化 + 主体与背景分离”目前暂时放弃；不得按既定计划推进接入，未来如要重启需重新获得用户确认。
- PC 生成预览新增可选像素画效果：严格格线识别时按原格取样；只有像素画外观信号时按拼豆格主色取样；无识别信号时禁用选项。该启发式能力不得自动改变默认效果，PAD 和手机端保持不可用。
- `algorithm-lab.html`、`algorithm-lab-complete.html`、`algorithm-lab-final.html`、`flatness-lab.html`、`combined-lab.html` 和实验函数只用于测试、比较与参数验证；其中 `flatness-lab.html` 可输出本地 PNG，但不应写入正式图纸、草稿或导出数据。
- PC 可选像素画效果需分别验证规则格线采样和不规则格线主色采样，确认预览与确认后的图纸完全一致，并用像素画、普通照片、渐变和含透明区域的图片检查误判、漏判及结果质量。该选项不改变正式默认方案。
- 任何算法要替换正式默认流程前，必须得到明确确认，并完成以下验证：
  - 与裁剪、尺寸、品牌、规格、颜色限制兼容。
  - 与预览确认、编辑、草稿恢复和导出兼容。
  - 使用代表性图片验证轮廓、颜色准确性（含亮度/饱和度偏移）、还原精准度、颜色数、孤立色块和生成耗时。
  - 按 `docs/FINAL_CANDIDATE_ALGORITHM_TEST_CHECKLIST.md` 和对应覆盖矩阵记录测试图片、特征与候选相对正式基准的结论；未覆盖的类型不得视为已验收。
  - 不降低 PC、PAD、手机端主流程稳定性。

## 5. 三端适配边界

- 允许 PC、PAD、手机各自拥有不同 UI，但功能语义和数据结果必须一致。
- PC 以完整编辑能力为优先。
- PAD 以大画布、触控和制作辅助为优先；设置、颜色与草稿面板不应长期压缩画布。
- 手机以分步操作、明确状态和安全触控为优先。
- 任何新增手势都必须避免与画布拖拽、缩放和编辑点击冲突。
- 固定标尺允许先进行 PC 优化，但不代表 PAD、手机端同步完成，也不允许以此为由移除其他端既有标尺能力。每次一键归档必须记录跨端同步状态及细节，直至实现和验收完成。

### 固定标尺专项回归

- 顶部与左侧标尺条固定在图纸视口边缘，顶部不得被标题栏遮挡；平移时刻度及数值与图纸坐标保持对应。
- 放大后能逐格显示数字，缩小后按 5、10、20 格降级，检查正数、负数及多位数是否清晰且不重叠。
- 原图对照开关、视口尺寸变化后，标尺范围及时更新，只覆盖右侧图纸画布。
- 检查缩放重置及其动画、拖拽、点击格子、画笔、吸管、橡皮、撤销/重做；标尺覆盖层不能拦截编辑输入。
- 检查 PAD、手机端的原有标尺可用性及导出结果；编辑器显示层变更不得悄悄改变导出图纸。

## 6. 高风险模块与最低验证

| 修改区域 | 修改后最低验证 |
| --- | --- |
| `src/processor.js` | 上传图片、不同尺寸、颜色限制、预览、最终生成、耗时与颜色统计。 |
| `src/renderer.js` / 画布事件 | 缩放、拖拽、点击格子、编辑模式、PC 与触控端。 |
| `src/editor.js` / `src/features/adjust.js` | 画笔、吸管、橡皮、批量替换、撤销、重做、暂存与确认。 |
| `src/ui.js` / `src/main.js` | 上传、裁剪、设置、生成、面板、草稿、导出。 |
| `index.html` / `css/style.css` | PC、PAD、手机的可见性、层级、点击与滚动。 |
| 草稿或导出逻辑 | 保存、恢复、导入、导出、图纸名称和颜色统计。 |

## 7. 开发前后的执行规则

开发前：

1. 阅读 `docs/PROJECT_CORE.md`、本文和最新开发归档。
2. 阅读将被修改函数的完整实现，并搜索所有调用方。
3. 判断本次属于普通样式调整还是核心流程变更。
4. 若属于核心流程变更，先提出影响说明与确认请求。

开发后：

1. 检查 JavaScript 语法与补丁格式。
2. 测试直接修改的功能及其关联流程。
3. 对涉及三端、画布、生成、草稿或导出的改动做对应回归。
4. 在归档中记录已确认决策、遗留风险和下一步验证。

## 8. 维护规则

每次“一键归档”时，检查本文是否仍与产品决策一致：

- 新确认的核心流程要写入。
- 已废弃的限制要删除或标记为历史。
- 实验能力转为正式能力时，要先更新本文，再更新核心说明书和归档。
- 如果一个规则不足以阻止高风险改动，补充具体的触发条件与验证项。
- 固定标尺跨端同步完成前，每次归档明确列出 PC 验收状态、PAD/手机未同步细节和剩余回归项；只有完成验证后才能关闭待办。
