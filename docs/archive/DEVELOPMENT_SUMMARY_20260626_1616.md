## 产品与商业判断

### 1. 当前项目价值判断

- 当前项目有真实使用价值，但还不是高壁垒状态。
- 价值主要来自垂直场景完整度，而不是图片转像素图本身。
- 如果只停留在“上传图片生成拼豆图纸”，容易被同类工具复制或稀释。
- 真正的竞争力应来自制作级体验、材料清单、移动/平板编辑体验、制作过程辅助、社区和材料闭环。

### 2. 长期方向确认

用户明确：生成图纸只是短期目标，用来积累和吸引用户；长期目标是做闭环，包括拼豆过程辅助、平台内跟做、社区化和平台化。

结论：

- 方向正确。
- 长期应从“生成器”转向“制作平台”。
- 关键差异点是拼豆制作过程辅助，而不是单纯生成图片。
- 如果用户只生成后下载离开，留存弱；如果用户制作过程也在平台内完成，就有进度、数据、社区和商业闭环。

### 3. 三端商业定位

- 手机：获客、浏览、分享、轻量入口。
- PC：生成、复杂编辑、导出、管理作品。
- iPad / 平板：制作过程核心端，承担留存和付费价值。

从商业角度看，平板端值得重点投入，因为它更贴近真实桌面制作场景。

## 上线与代码保护讨论

### 1. GitHub Pages 与私有仓库

- GitHub Free 下公开 Pages 通常意味着仓库或发布代码存在暴露风险。
- 付费 GitHub 可支持私有仓库 Pages，但发布出来的前端网页仍会被浏览器下载。
- 私有仓库只能保护仓库源码、提交记录、开发文档，不能保护前端运行代码。

### 2. 短期体验版建议

用户暂时不想充值 GitHub。

建议短期方案：

- 仓库保持私有。
- 生成干净发布版目录。
- 不发布 `docs/archive`、开发记录、未用脚本。
- JS/CSS 做压缩或混淆。
- 部署到 Vercel、Netlify、Cloudflare Pages 等免费/低成本静态托管。
- 体验链接只发给少量可信用户。

这不能彻底防复制，但适合短期体验版。

### 3. 后端化准备

如果要真正保护核心逻辑，需要将核心生成逻辑后端化。

第一阶段建议只后端化：

- 图片上传。
- 参数接收。
- 像素化。
- 调色板匹配。
- 颜色数量限制。
- 返回 `pixelData`、尺寸、颜色统计。

暂时不搬：

- 草稿箱。
- 手动编辑。
- 撤回。
- 颜色清单交互。
- 导出图纸。
- 社区/账号。

推荐路线：

- Node.js + Express。
- 图片处理用 `sharp`。
- 前端继续静态页面。
- 生成按钮改为调用 `POST /api/generate`。

## 三端独立 UI 架构

### 1. 设计原则确认

后续项目不建议继续在同一套 DOM 上硬改响应式样式。

目标架构：

- 同一个入口页面。
- PC / iPad / 手机各自有独立 UI 外壳。
- 功能逻辑共用。
- 每端可以自由设计布局、菜单、弹窗、工具栏。

允许不同：

- 布局。
- 菜单形式。
- 弹窗形式。
- 工具栏。
- 页面层级。
- 导航方式。
- 文案密度。
- 横竖屏策略。

不建议不同：

- 同一功能的结果。
- 草稿数据结构。
- 导出格式。
- 编辑撤回规则。
- 颜色匹配算法。
- 图纸坐标体系。

### 2. 本次完成的第一阶段重构

本次完成的是“三端外壳骨架”，不是最终三端独立 UI。

当前实现方式：

- 保留同一套真实功能节点，避免重复 ID 和重复事件绑定。
- 根据断点创建并激活：
  - `workbench-desktop-shell`
  - `workbench-tablet-shell`
  - `workbench-mobile-shell`
- 当前端类型变化时，将现有功能节点挂载到 active shell。
- PC、iPad、手机后续可以分别以各自 shell 作为样式锚点。

新增状态：

- `AppState.workbenchViewportMode`

跨端切换时会关闭临时 UI：

- 草稿菜单。
- 生成设置/颜色清单浮层。
- 调色盘浮层。
- 调色盘拖动状态。
- 原图对照拖动状态。

但不会丢失：

- 图纸数据。
- 草稿数据。
- 编辑数据。
- 当前生成结果。
