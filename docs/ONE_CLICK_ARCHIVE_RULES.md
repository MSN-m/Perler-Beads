# 一键归档规则（跨项目通用版）

> 用途：将本文件交给其他项目的 AI，或在该项目的 `AGENTS.md` 中引用，使不同会话能够准确交接工作。
> 本规则提炼自拼豆项目的归档约定与实践，已去除具体业务、技术栈和机器路径。其他项目可调整路径，但应保留状态区分和证据要求。

## 1. 触发与范围

用户明确说“一键归档”时，执行会话归档：回顾本次会话的改动、讨论、确认、验证、回退和未完成事项，生成可供下一次会话继续工作的 Markdown 文档。

归档不是 Git 提交、发布、部署、备份或清理操作。除非用户另有明确授权，不执行 `git add`、`git commit`、`git push`、发布部署，不删除文件或用户数据，不借归档继续开发尚未授权的功能。

用户仅要求解释归档规则、制作规则文件或提供模板时，不视为触发一次正式开发归档。

## 2. 开始前读取项目上下文

按以下顺序阅读：

1. `AGENTS.md`：项目开发与协作规则。
2. `docs/PROJECT_CORE.md`：已确认的产品事实、功能定义和长期决策。
3. `docs/PRODUCT_GUARDRAILS.md`：受保护流程、正式与实验边界、必要回归要求。
4. `docs/archive/DEVELOPMENT_SUMMARY_*.md` 中时间最新的一份：最近进度和遗留事项。

如果项目使用不同名称，读取其对应文件。缺失时明确记录缺失，不假装已读；需要创建核心文档时，只写有依据的事实，将未知内容标为待确认。

核心说明书是已确认产品事实的依据，旧归档不能覆盖已确认的核心决策。最新用户明确指令用于识别决策变更；无法确定冲突是否已被明确解决时，询问用户，不自行选择一个版本。

## 3. 收集事实

- 回顾整个当前会话，不只总结最后一条需求。
- 核对实际文件和相关差异；有 Git 时可读取 `git status`、`git diff` 等，不改变暂存区。
- 区分本轮改动、会话开始前已有改动和无法确定来源的改动；不能把整个工作区差异都归为本轮成果。
- 核对新增、修改、删除文件和最终保留内容；未跟踪文件也要检查，不能仅依赖 `git diff`。
- 记录用户确认、待确认建议、实验结果、撤回及放弃的方案。
- 收集实际运行的测试、浏览器或设备检查及其结果。历史测试注明时间或来源，不描述为本轮重新运行。
- 没有代码改动也可以归档讨论和决策，但必须写明“本轮未修改业务代码”。

## 4. 明确区分状态

| 状态 | 归档时应写清楚 |
| --- | --- |
| 已实现且已验证 | 最终行为、代码位置、验证范围和结果 |
| 已实现但待验收 | 已接入部分，以及尚未验证的路径或设备 |
| 已确认但未实现 | 用户决定、实施边界、后续所需工作 |
| 仅讨论或待确认 | 候选方案，不能当作授权或正式产品事实 |
| 实验能力 | 所在实验入口、效果和局限，不自动推广到正式流程 |
| 已回退或已放弃 | 回退范围、最终保留状态，以及是否禁止自动重启 |
| 已知问题或阻塞 | 现象、影响、证据、缺少的条件和下一步 |

禁止把“界面完成”写成“功能全部完成”，把“单测通过”写成“全部设备验收通过”，把“请求下载”写成“文件已落盘”，或把“建议”写成“用户已确认”。

## 5. 生成归档文件

保存位置：

`docs/archive/DEVELOPMENT_SUMMARY_YYYYMMDD_HHMM.md`

使用用户或项目约定的时区，并在正文注明时区。不要覆盖已有同名归档；发生同分钟重名时，可追加 `_02` 等编号并说明。

至少包含：

1. 当前结论与本轮范围。
2. 功能变更及已确认决策。
3. 修改文件清单及各文件用途。
4. 验证记录与限制。
5. 已知 Bug、风险和未完成事项。
6. 下一步计划及继续工作所需条件。
7. 核心文档同步情况。
8. 工作区与 Git 状态，例如是否仍未暂存、是否实际提交。

文档应让没有读过会话的新 AI 看懂：现在是什么状态、哪些可以继续、哪些仍需用户决定、哪些不应再次尝试。

## 6. 同步长期文档

每次归档都检查下面两份文档是否需要同步；不是每次都必须修改。

### `docs/PROJECT_CORE.md`

当本轮确立长期产品事实、功能语义、流程决定、端差异或正式实现边界时，更新对应章节。保留“已实现但未验收”等准确状态，不把临时过程和未经确认的建议写成稳定事实。

### `docs/PRODUCT_GUARDRAILS.md`

当本轮新增受保护规则、数据安全约束、正式与实验边界或必要回归要求时，更新对应章节。应具体说明保护什么、什么行为需要确认，以及应检查哪些路径。

同步时修正已被明确替代的旧规则，标明覆盖关系，避免两条相互矛盾的规则同时看起来有效。历史过程留在归档中，不无条件堆入核心文档。

归档必须逐项说明两份文档“已更新及更新内容”或“未更新及原因”；缺失时说明处理方式。

## 7. 保留遗留事项和验证边界

- 从上一份归档继承仍有效的未完成事项，不能因为本轮未涉及就删掉。
- 只有获得相应完成证据后才能关闭待办；写明关闭依据。
- 已放弃方案单独保留其结论，不作为下一次自动继续的待办。
- 分别记录自动测试、浏览器交互、模拟视口和真实设备验证。某端通过不能代表其他端通过。
- 工具、权限、环境或用户未保存状态导致无法验证时，说明具体限制；不得为验证而丢弃用户内容。
- 归档无需机械重跑全部测试；记录已有证据，必要时执行与当前改动相关、已获授权的检查。
- 保留关键失败原因与纠正结果，尤其是防止下一位 AI 重复错误所需的信息。

## 8. 交付前检查

- 文件已实际写入，路径、日期和编码正确，遵循目标项目换行规范。
- 文件清单与最终保留改动一致，没有把已回退内容列为上线成果。
- 结论、测试数量和覆盖范围有依据，无法确认的内容明确标注。
- 旧待办、实验边界、用户放弃事项和待确认问题没有丢失。
- 核心文档与归档不矛盾，且写明同步情况。
- 不写入 API key、令牌、密码或不必要的个人信息。
- 最终回复提供归档文件链接，简述核心文档同步情况与重要遗留事项，不声称已提交或发布，除非确实执行成功。

## 9. 开发归档模板

以下模板供收到“一键归档”指令时使用；根据实际内容删改，不用虚构内容填满章节。

```markdown
# 开发归档：<本轮主题>

时间：<YYYY-MM-DD HH:MM，时区>

## 1. 当前结论与范围

<最终保留成果、未实施内容和本轮边界>

## 2. 功能变更与决策

- 已实现：<行为、入口、适用端、验证状态>
- 已确认未实现：<决定与边界>
- 待确认：<讨论内容，不作为实施授权>
- 实验／回退／放弃：<最终状态及不要自动继续的事项>

## 3. 修改文件清单

| 文件 | 变更与用途 | 状态／归属 |
| --- | --- | --- |
| <路径> | <说明> | <本轮新增／修改／删除，或已有改动> |

## 4. 验证记录与限制

- <实际命令或操作、结果、时间或来源>
- <浏览器、设备、场景覆盖>
- <未验证范围、失败或环境限制>

## 5. 已知问题与未完成事项

- <继承或新增的问题、影响及证据>
- <已关闭事项及关闭依据，如有>

## 6. 下一步计划

1. <可以继续的工作及必要条件>
2. <仍需用户决定的内容>

## 7. 文档同步情况

- PROJECT_CORE.md：<已更新内容／未更新原因／缺失处理>
- PRODUCT_GUARDRAILS.md：<已更新内容／未更新原因／缺失处理>

## 8. 工作区与提交状态

<实际暂存、提交、推送及部署情况；无法确认则说明>
```

## 10. 给其他项目 AI 的接入说明

可将本文件复制到目标项目的 `docs/ONE_CLICK_ARCHIVE_RULES.md`，再在该项目 `AGENTS.md` 中加入：

```markdown
## 一键归档

用户说“一键归档”时，按 docs/ONE_CLICK_ARCHIVE_RULES.md 执行。
会话开始依次阅读 AGENTS.md、docs/PROJECT_CORE.md、
docs/PRODUCT_GUARDRAILS.md 和最新的 docs/archive/DEVELOPMENT_SUMMARY_*.md。
归档时核对实际改动与验证证据，同步必要的长期文档，保留有效遗留事项。
一键归档本身不授权 Git 暂存、提交、推送、发布、部署或数据清理。
```
